# Axhub Make 二次改造规范

适用于本仓库的本地二次改造、上游升级，以及影响本地 Axhub Make 运行的仓库外启动器和脚本。改造开始前查阅 [改造索引](README.md)、相关档案及 [上游基线](UPSTREAM.md)。

## 实施前核对

- 对照上游基线、当前源码和工作区差异。可用 `git show <上游基线>:<路径>` 查看原实现。沿实际入口核对调用方、数据、配置、扩展点和测试，保留用户已有改动。涉及 `client/` 时也遵循该目录的规则。
- 遇到启动、预览或 AI 行为问题，先核实实际运行的是外层安装包、本地源码构建还是生成的客户端，再定位负责该行为的代码。修改生成文件时，从生成脚本或输入配置改起，再重新生成产物。
- 本地需求与原设计冲突时，说明原有行为及其用途、冲突点、兼容影响和可选方案。涉及公共接口、持久化数据或升级成本时，说明旧调用方和旧数据如何继续使用。

## 方案选择

优先沿用原项目的组件、接口、数据结构和调用链。按以下顺序评估，选择能满足本次需求且容易验证、维护和升级的最小改动。

| 优先级 | 方式 |
| --- | --- |
| P0 | 直接复用原有能力 |
| P1 | 使用已有配置、参数或开关 |
| P2 | 使用已有插件、事件或扩展入口 |
| P3 | 通过职责明确的适配器或独立模块接入 |
| P4 | 局部修改原生实现，记录采用它的理由和影响 |
| P5 | 调整核心架构，实施前说明限制、影响和回退方式并取得用户明确授权 |

当扩展方案依赖更多内部细节、改变更多调用路径或更难回退时，可以选择 P4 并在档案中说明取舍。全局覆盖或替换核心对象须先证明缺少合理替代方案并取得明确授权。避免无关重构、格式化、依赖更新和生成产物变更。

需要独立启停或让两种行为长期并存时，使用集中的配置入口。新增开关应尽量默认保持原生行为，关闭后验证能恢复原有路径。局部缺陷修复可通过独立的改动范围实现回退。涉及持久化变更时，实施前核对旧数据兼容和恢复步骤，说明无法完整恢复的部分。

## AI 工作流审批

任何可能改变 AI 工作流行为的改造，实施前都要沿实际调用链核对影响。典型范围包括任务输入、提示词、上下文和历史消息、模型选择及参数、智能体编排、工具注册与执行、权限、请求和响应协议、流式输出、中断、重试及降级。界面、启动配置和适配层对这些行为的间接影响同样适用。

确实会改变上述行为时，先说明涉及的文件、入口、调用链、预期变化、风险、回退方式及验证计划，取得用户明确授权后再实施。影响未查清时继续追踪。只读分析和经核实的纯展示调整可按日常流程处理。Axhub Make 自身在运行时读取的智能体指令和提示词属于这条保护范围。

## 改造档案

每项改变功能、业务规则、交互、配置语义、接口、数据结构或项目实际运行行为的本地改造，都必须在交付前把 Markdown 档案保存到 `docs/customizations/changes/`。档案随改造更新，即使尚未提交 Git。仓库外启动器的行为变更同样登记，并人工核对外围文件差异。

- 同一改造后续修复或调整时更新原档，按日期追加变更内容和原因。独立事项使用下一个未使用的 `CUST-xxx` 编号，从 [档案模板](TEMPLATE.md) 建档并加入 [改造索引](README.md)。状态或摘要变化时同步索引。
- 写清需求、原生行为、改动日期、实际做法及原因、关联文件和关键代码入口、兼容和升级影响、验证结果及回退步骤。分开记录方案、代码证据和验收结果。有提交号时附上可核实的引用，待提交时标注未提交。
- 纯排版、行尾和其他无语义的机械维护可豁免，交付时说明依据。原样上游同步在 [升级记录](UPGRADE_LOG.md) 登记版本和验证。同步导致本地行为变化时更新对应档案。测试变更与所验证的行为关联，单独补测试可说明其维护性质。

## 验证与登记检查

按风险验证实际使用入口、改造场景、受影响的原有行为，以及适用的旧数据、接口兼容、开关关闭和回退路径。AI 工作流需验证原有路径和新增路径，覆盖受影响的工具调用、异常及中断场景。记录实际运行的版本、配置或构建产物，以及测试命令和结果。把未运行、失败和待实际使用验收的场景写进档案。

交付前对照实际差异、档案和索引，在源码仓库运行 `node scripts/check-customizations.mjs [比较基线]`。该命令默认与 `HEAD` 比较，检查暂存和工作区差异及未跟踪文件，按仓库相对路径匹配本次新增或更新的档案。已提交变更需传入任务开始前的提交。接手已有未提交改动时，先记录任务开始前的差异，人工区分本次范围，单列既有差异造成的检查结果。

脚本检查档案结构和路径匹配。共享文件涉及的每项行为、仓库外改动和豁免项由人工复核。交付时说明改造编号、实际结果、验证和兼容风险。

按 [上游基线与升级流程](UPSTREAM.md) 评估文件变动和行为冲突。提交、推送、合并、变基、重置及覆盖须有明确授权。

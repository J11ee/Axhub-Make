# CUST-004 Windows 本地启动与前端产物加载

- 模块：工作区外围 Windows 启动器
- 类型：外围新增
- 状态：已实现
- 首次可追溯的故障记录：2026-11-11（启动器首次创建时间待核实）
- 最近更新：2026-11-17

## 原始需求和原生行为

旧服务复用与安装包静态目录使双击启动后仍可能看到旧前端。用户要求启动器自动检查并按需构建最新产物。上游 README 提供 `npx -y @axhub/make@latest`、后台启动和完整源码开发服务入口。

## 实际实现

工作区外层的 `启动 Axhub Make.cmd` 进入启动器目录并调用 `start-make.ps1`。PowerShell 脚本按源码与产物时间或 `ForceBuild` 判断是否调用 Vite（前端构建工具），同步管理端构建产物，再通过外层安装包的 CLI（命令行入口）以 `--admin-root` 指向内层 `dist/admin`，在指定回环地址后台启动，并处理已有服务及过期服务记录。内层源码为 0.6.22，外层已安装的 CLI 包为 0.6.23。

2026-11-17 起，启动器统一使用内层源码的 `node --import tsx bin/cli.mjs` 和对应的 `dist/admin`。前端按原规则检测并构建，启动时使用已有的 Make 全局状态目录与项目登记。若端口仍由原启动器的外层安装包使用，先核对 PID 和 CLI 路径，再替换为本地源码服务。原服务记录在确认归属后更名备份。原因是外层 0.6.23 后端没有页面 PRD 接口，加载新版前端后点「确认关联」会得到 `404 Not found`。

2026-11-17 修正按需构建判断。Vite 构建失败时，收尾插件仍可能更新 `dist/admin/index.html`，导致下次启动误以为构建已成功并继续加载旧脚本。启动器现以 `dist/admin/.build-succeeded` 的时间与 `src/` 比较，构建前清除旧标记，只在 Vite 成功退出后重新写入。缺少标记时，下次启动会重新构建。

## 关联路径

## 历史证据

Codex 的早期记录涉及项目根目录不匹配和修复尝试。Antigravity 后续排查旧界面问题，按用户要求增加按需构建，并记录了产物同步、`--admin-root` 与重启选项。

旧版自动将过期记录更名为 `.stale-<GUID>` 后重试，状态为「已被替代」。现行脚本使用健康检查并删除过期记录后重试。旧脚本的历史快照可作为恢复线索，旧备份分支缺乏运行验收证据。见 [历史审计](../LEGACY_AUDIT.md)。

## 上游升级影响

确认 CLI 参数和健康接口、进程记录、管理端资源和 API（应用接口）的兼容性，以及版本升级后产物与服务是否来自预期位置。考虑回归上游入口时，先确认新入口仍会加载本地前端产物。脚本按 `src/` 时间判断构建，改动其他构建输入时需留意是否触发重建。

## 验证与遗留

2026-11-16 核对了脚本及版本，PowerShell 语法解析通过。真实启动和服务复用待实测。Git 登记命令仅覆盖源码仓库，外围文件由人工核对。启动器包含停止进程和删除陈旧运行记录的分支，实际升级时应按确认过的环境验收。

2026-11-17 在独立状态目录和端口 53832 验证源码服务后台启动和再次启动复用。随后在原端口 53817 完成迁移，实际项目 API 与管理端资源均可读取，启动器再次运行时复用新服务。页面绑定验证记录见 CUST-005。未执行全量 AI 工作流验收。

2026-11-17 构建判断修复后，依赖缺失导致的构建失败未生成成功标记。锁定版本的包文件和链接恢复后，由 `start-make.ps1 -NoOpen` 成功构建并重启 53817，HTTP 返回的管理端脚本与新产物一致。再次运行启动器跳过构建并复用服务 PID。构建仍有依赖注解、CSS 压缩及大块警告，未执行自动化测试和浏览器交互验收。

## 回退

停止源码服务后，可恢复本次保存的原 `start-make.ps1`，或按历史安装包命令启动。恢复旧服务和旧管理端产物后，页面 PRD 接口不可用，已经保存的绑定和正文继续保留在项目目录。

单独回退构建判断时，恢复用 `index.html` 时间判断的代码段即可。
